# Архитектура WMS-системы

## 1. Общие принципы

Проект построен на принципах **Clean Architecture** (также известной как Hexagonal Architecture). Это обеспечивает:

- **Независимость от внешних фреймворков** (база данных, веб-интерфейс, UI).
- **Тестируемость бизнес-логики** без привязки к инфраструктуре.
- **Гибкость** – замена технологий (например, переход с PostgreSQL на SQL Server) не требует изменений в бизнес-слое.
- **Чёткое разделение ответственности** между слоями.

Архитектура состоит из четырёх основных слоёв:

1. **Core** – ядро (доменные сущности, интерфейсы репозиториев и сервисов, перечисления, исключения).
2. **Infrastructure** – реализация доступа к данным, Identity, миграции.
3. **Services** – бизнес-логика, реализация сервисов.
4. **API** – контроллеры, DTO, маппинг, настройка DI, middleware.

Правило зависимостей: зависимости направлены **внутрь** – каждый слой может ссылаться только на внутренние слои, но не на внешние.

```
API → Services → Core
Infrastructure → Core
Services → Core
```

API знает о Infrastructure только через DI (регистрация реализаций), но не использует его типы напрямую.

---

## 2. Описание слоёв

### 2.1. Core (Wms.Core)

**Назначение:** содержит бизнес-сущности и контракты (интерфейсы), не зависящие от внешнего мира.

**Содержит:**
- **DTOs** - DTO для передачи данных между слоями (например, `ExpiringBatchInfo`, `LowStockProductInfo`) 
- **Entities** – доменные модели: `Warehouse`, `Zone`, `Rack`, `Shelf`, `Cell`, `Product`, `Batch`, `InventoryTransaction`, `Notification`, `ApplicationUser` (наследует `IdentityUser`).
- **Enums** – перечисления: `ZoneType`, `TransactionType`, статусы документов.
- **Interfaces** – контракты для репозиториев и сервисов. Базовые интерфейсы сервисов:
  - `IReadOnlyService<T>` – только методы чтения (`GetAll`, `GetById`).
  - `ICrudService<T>` – наследует `IReadOnlyService<T>` и добавляет методы изменения (`Create`, `Update`, `Delete`).
- **Options** – классы конфигурации (например, `JwtSettings`).
- **Exceptions** – пользовательские исключения.

**Зависимости:**
- `Microsoft.AspNetCore.Identity.EntityFrameworkCore` – для `ApplicationUser` (компромисс, позволяющий использовать Identity без привязки к Infrastructure).
- Никаких других внешних зависимостей.

---

### 2.2. Infrastructure (Wms.Infrastructure)

**Назначение:** реализация доступа к данным и интеграция с внешними системами.

**Содержит:**
- **Data/ApplicationDbContext** – наследник `IdentityDbContext<ApplicationUser>`, объединяет Identity и бизнес-таблицы.
- **Data/Configurations** – Fluent API-конфигурации сущностей (связи, индексы, ограничения).
- **Repositories** – реализация обобщённого репозитория `Repository<T>` и специфических репозиториев (`ZoneRepository`, `RackRepository`, `CellRepository`, `ProductRepository`).
- **Migrations** – миграции Entity Framework Core.
- **Data/Seed/DbInitializer** – инициализация ролей и учётной записи Chief.

**Зависимости:**
- `Npgsql.EntityFrameworkCore.PostgreSQL` – провайдер PostgreSQL.
- `Microsoft.AspNetCore.Identity.EntityFrameworkCore` – интеграция Identity.
- `Wms.Core` – реализует интерфейсы репозиториев.

---

### 2.3. Services (Wms.Services)

**Назначение:** реализация бизнес-логики приложения.

**Содержит:**
- `ReadOnlyService<T>` – реализует `IReadOnlyService<T>` и предоставляет базовую логику для методов чтения через репозиторий.
- `CrudService<T>` – наследует `ReadOnlyService<T>` и реализует `ICrudService<T>`, добавляя методы создания, обновления и удаления с сохранением в базу.
- **Специфические сервисы-справочники** (`ProductService`, `WarehouseService`, `ZoneService`, `RackService`, `ShelfService`, `CellService`) наследуют `CrudService<T>` и реализуют свои интерфейсы. Они могут добавлять уникальные методы (например, `GetByCategoryAsync` для `ProductService`).
- **Сервисы для сущностей со статусами** (`ReceiptService`, `SupplyRequestService`, `SupplyOrderService`) не используют общие базовые классы, а реализуют кастомные интерфейсы с явными бизнес-операциями.
- **Сервис для Batch** (`BatchService`) наследует `ReadOnlyService<Batch>` и реализует `IBatchService`, добавляя только методы `MoveBatchAsync` и `GetBatchesWithFiltersAsync`.
- **Сервис аудита (`InventoryTransactionService`)** реализует `IInventoryTransactionService`, обеспечивая создание записей аудита и их фильтрацию для просмотра.
- **Сервис уведомлений (`NotificationService`)** – реализует `INotificationService`: получение уведомлений пользователя, отметка о прочтении, удаление, а также массовое создание уведомлений для всех менеджеров.
- **Фоновый сервис (`NotificationBackgroundService`)** – периодически (каждый час) проверяет сроки годности и низкие остатки, создаёт уведомления для всех менеджеров.
- **Auth/JwtService** – реализация генерации JWT-токенов.
- **BackgroundServices** – фоновые задачи (уведомления о сроках годности, низких остатках).
- **Валидаторы** – если используем FluentValidation.

**Зависимости:**
- `Wms.Core` – интерфейсы сервисов и репозиториев.
- `Microsoft.Extensions.Options` – для доступа к конфигурации `JwtSettings`.
- `System.IdentityModel.Tokens.Jwt` – для генерации токенов.
- `Microsoft.AspNetCore.Identity` – для работы с `UserManager` и `RoleManager` (используются в `AuthController`, но сервис `JwtService` получает только `ApplicationUser` и роли как строки, не завися от Identity напрямую).

**Принцип:** сервисы не зависят от Infrastructure напрямую, только от абстракций (интерфейсов репозиториев), что позволяет легко заменять реализацию.

---

### 2.4. API (Wms.API)

**Назначение:** точка входа в приложение, предоставление RESTful API.

**Содержит:**
- **Controllers** – контроллеры.
- **DTOs** – объекты передачи данных (запросы/ответы).
- **MappingProfiles** – настройки AutoMapper для преобразования Entity ↔ DTO.
- **Options** – классы для привязки конфигурации.
- **Middlewares** – глобальная обработка исключений, логирование.
- **Extensions** – методы расширения для регистрации сервисов в DI.
- **Validators** – классы валидации на основе FluentValidation для всех входных DTO.
- **Program.cs** – настройка хоста, DI, конвейер middleware.

**Зависимости:**
- `Wms.Services` – для внедрения сервисов.
- `Wms.Infrastructure` – для регистрации DbContext и репозиториев (через DI).
- `AutoMapper.Extensions.Microsoft.DependencyInjection` – для маппинга.
- `Swashbuckle.AspNetCore` – для Swagger/OpenAPI.
- `Microsoft.AspNetCore.Authentication.JwtBearer` – для JWT-аутентификации.

Контроллеры разделены на две категории:
- **Справочники** (`ProductController`, `WarehouseController`, `ZoneController`, `RackController`, `ShelfController`, `CellController`) наследуют `BaseCrudController` и предоставляют полный CRUD.
- **Контроллеры со статусами** (`ReceiptController`, `SupplyRequestController`, `SupplyOrderController`) и **контроллер для Batch** (`BatchController`) не используют общий базовый класс, а реализуют только необходимые эндпоинты (например, `POST /api/receipts`, `PUT /api/receipts/{id}/receive` и т.д.). Это соответствует бизнес-правилам и исключает нежелательные операции.

## 3. Ключевые архитектурные решения

### 3.1. Единый контекст базы данных (`ApplicationDbContext`)

**Решение:** наследовать `IdentityDbContext<ApplicationUser>` и добавить `DbSet` для всех бизнес-сущностей в один контекст.

**Обоснование:**
- Упрощает управление миграциями и транзакциями.
- Все таблицы физически находятся в одной базе данных, что естественно для монолита.
- Identity и бизнес-данные легко связываются (например, `InventoryTransaction.UserId` ссылается на `AspNetUsers`).
- Не требуется дополнительная настройка для согласованности данных.

**Альтернативы:** разделение на два контекста (Identity и бизнес) рассматривалось, но отвергнуто из-за излишней сложности для текущих требований.

---

### 3.2. Базовые классы сервисов и контроллеров

**Репозиторий:** `IRepository<T>` с реализацией `Repository<T>` предоставляет базовые методы доступа к данным (`GetAll`, `GetById`, `Add`, `Update`, `Delete`, `SaveChanges`). Все специфические репозитории наследуют его и добавляют свои методы (например, загрузку навигационных свойств).

**Сервисы:**
- `ReadOnlyService<T>` – реализует только чтение и используется для сущностей, которые не должны изменяться напрямую (`Batch`, а также, возможно, `Reservation`).
- `CrudService<T>` – для справочников, где разрешён полный CRUD. Он наследует `ReadOnlyService<T>` и добавляет методы изменения. Конкретные сервисы переопределяют `DeleteAsync`, чтобы добавить проверки зависимостей.

**Контроллеры:**
- `BaseReadOnlyController<TEntity, TDto>` – предоставляет эндпоинты `GET` (все и по id) для сущностей только на чтение.
- `BaseCrudController<TEntity, TDto, TCreateDto, TUpdateDto>` – наследует `BaseReadOnlyController` и добавляет эндпоинты `POST`, `PUT`, `DELETE` для справочников. Использует `ICrudService<TEntity>`.

**Преимущества такого подхода:**
- Чёткое разделение ответственности: каждая сущность получает только разрешённые операции.
- Безопасность – невозможно случайно вызвать `Update` для `Batch` или изменить статус документа через `PUT`.
- Упрощение тестирования и поддержки – бизнес-правила локализованы в явных методах сервисов.
- Уменьшение дублирования кода для справочников.

---

### 3.3. JWT-аутентификация

**Решение:** использование `Microsoft.AspNetCore.Authentication.JwtBearer` с симметричным ключом.

**Обоснование:**
- Stateless, подходит для REST API.
- Интегрируется с ASP.NET Core Identity (получение ролей, проверка пользователя).
- Легко масштабируется (токен содержит все необходимые claims).
- Поддерживает ролевую модель (через `ClaimTypes.Role`).

**Хранение секрета:** в `appsettings.json` (для разработки), в продакшене – через переменные окружения или Azure Key Vault.

---

### 3.4. AutoMapper для маппинга

**Решение:** использование AutoMapper с централизованным `MappingProfile`.

**Обоснование:**
- Сокращает шаблонный код ручного присвоения свойств.
- Все правила маппинга собраны в одном месте, легко поддерживать.
- Поддерживает проекции в EF Core (`ProjectTo`), что оптимизирует запросы (выбираются только нужные поля).

**Альтернативы:** ручное копирование или использование библиотек типа Mapster – но AutoMapper широко распространён и имеет хорошую документацию.

---

### 3.5. Использование `AsNoTracking()` для чтения

**Решение:** во всех репозиториях методы `GetAllAsync` и `FindAsync` используют `AsNoTracking()`.

**Обоснование:** данные, предназначенные только для чтения, не должны отслеживаться контекстом, что повышает производительность и предотвращает случайные изменения.

**Исключение:** при получении сущности для обновления (например, `GetByIdAsync` без `AsNoTracking`) используется отслеживание, чтобы EF Core мог корректно применить изменения.

---

### 3.6. Передача `CancellationToken`

**Решение:** все асинхронные методы принимают `CancellationToken` с параметром по умолчанию.

**Обоснование:** обеспечивает корректную отмену операций при длительных запросах или завершении работы приложения, улучшает отзывчивость и использование ресурсов.

---

### 3.7. Иерархическая структура склада

**Решение:** жёсткая иерархия Warehouse → Zone → Rack → Shelf → Cell, с каскадным удалением.

**Обоснование:** упрощает навигацию и адресацию ячеек (адрес формируется как Rack.Shelf.Cell). Каскадное удаление гарантирует целостность данных при удалении родительских объектов.

**Ограничения:** уникальность кодов стеллажей в пределах зоны, номеров полок в пределах стеллажа, кодов ячеек в пределах полки обеспечивается составными индексами.

---

### 3.8. Обработка исключений

**Решение:** глобальный middleware для перехвата необработанных исключений и возврата `ProblemDetails`. 
В middleware также обрабатываются исключения валидации (`ModelValidationException`), которые возвращают статус `400 Bad Request` с деталями ошибок в формате `application/problem+json`. Это обеспечивает единообразный формат ответов для всех типов ошибок.

**Обоснование:** единообразный формат ошибок, скрытие деталей внутренних исключений от клиента, логирование ошибок.

---

### 3.9. Валидация входных данных

Для валидации запросов используется библиотека `FluentValidation`.
Валидаторы создаются для каждого DTO, используемого в операциях создания и обновления (например, `CreateProductRequest`, `ReceiveReceiptRequest`).
В контроллерах валидация выполняется явно (через вызов `ValidateAndThrowAsync`) или через базовый класс `BaseCrudControllerWithValidation`, который автоматически проверяет DTO перед передачей в сервис.
При нарушении правил генерируется `ModelValidationException`, которое перехватывается глобальным middleware и возвращает клиенту структурированный ответ.

## 4. Схема базы данных (ключевые связи)

```
ApplicationUser (Identity) ─┬─ AspNetRoles
                            └─ InventoryTransaction (UserId)
Warehouse ──< Zone ──< Rack ──< Shelf ──< Cell
Cell ──< Batch (CellId)
Product ──< Batch (ProductId)
Batch ──< InventoryTransaction (BatchId)
Batch ──< Reservation (BatchId) – будет добавлено позже
Receipt ──< ReceiptLine (продукты)
SupplyOrder ──< OrderLine (продукты) + Reservation
SupplyRequest ──< RequestLine (продукты)
```

**Все связи настроены через Fluent API с каскадным удалением и индексами для уникальности.**

## 5. Потоки данных и бизнес-процессы

- **Приёмка (Receipt):**  
  Менеджер создаёт ожидаемую поставку. Работник подтверждает фактическое количество, указывает ячейку, дату производства/годности, цену. Создаётся `Batch`, ячейка помечается занятой, создаётся транзакция `In`.

- **Резервирование:**  
  При подтверждении заказа на отгрузку (`SupplyOrder.Confirm`) система ищет доступные партии (Quantity - ReservedQuantity) и создаёт записи `Reservation`, обновляя `Batch.ReservedQuantity`.

- **Отгрузка (Shipping):**  
  При переводе заказа в `Shipped` списывается `Quantity` (уменьшается на зарезервированное количество), удаляются резервы, создаются транзакции `Out`, ячейка освобождается, если партия стала пустой.

- **Перемещение:**  
  Изменяется `Batch.CellId`, создаётся транзакция `Move` с указанием старой и новой ячейки, обновляются флаги занятости ячеек.

- **Списание просрочки:**  
  Фоновый сервис находит партии с `ExpiryDate <= Today`, создаёт уведомления менеджерам. При ручном списании создаётся транзакция `WriteOff`, уменьшается `Quantity`, ячейка освобождается.

- **Аудит (InventoryTransaction):**  
  Каждая операция, меняющая `Quantity` (приход, расход, списание) или перемещающая партию (`Move`), создаёт запись в `InventoryTransaction` с типом `In`, `Out`, `Move` или `WriteOff`. Запись содержит `UserId`, `DocumentId` (ссылка на Receipt или SupplyOrder), временную метку, а для перемещений – старую и новую ячейки.

- **Уведомления:**  
  Фоновый сервис проверяет срок годности (≤3 дня) и остатки (ниже порога) и создаёт уведомления для менеджеров.

## 6. Безопасность и авторизация

- **JWT-токены** выдаются при успешном логине (эндпоинт `/api/auth/login`).
- Токен содержит `sub`, `email`, `name` и роли (`ClaimTypes.Role`).
- Политика авторизации на основе ролей:
  - `Chief` – полный доступ ко всем операциям, включая управление пользователями.
  - `Manager` – CRUD товаров, создание заявок на закупку, управление ячейками, перемещение, списание, подтверждение приёмки.
  - `Worker` – просмотр, подтверждение отгрузки и приёмки.
  - `StoreDirector` – создание заявок на поставку и просмотр их статуса.
- Все эндпоинты, кроме `login` и `register`, требуют аутентификации (`[Authorize]`).

---

## 7. Масштабируемость и будущие улучшения

- **Разделение на микросервисы** – при необходимости можно выделить модули (например, аудит, уведомления) в отдельные сервисы, сохранив Core как общую библиотеку.
- **Кэширование** – можно добавить Redis для часто запрашиваемых данных (справочники).
- **Event-driven архитектура** – использовать сообщения (RabbitMQ/Kafka) для асинхронной обработки уведомлений и аудита.
- **Интеграционные тесты** – покрытие ключевых сценариев (приёмка, резервирование) для повышения надёжности.

---

## 8. Заключение

Данная архитектура обеспечивает чистоту, тестируемость и гибкость. Она соответствует современным стандартам разработки на .NET и готова к дальнейшему расширению. Все архитектурные решения задокументированы и обоснованы, что упрощает вход новых разработчиков в проект.
