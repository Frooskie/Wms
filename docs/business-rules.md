# Бизнес-правила WMS

## 1. Общие принципы

- Все изменения остатков товаров должны быть задокументированы с помощью **InventoryTransaction** для обеспечения полного аудита.
- Операции выполняются в рамках транзакций базы данных — либо все изменения применяются, либо ни одно (атомарность).
- Аутентификация и авторизация осуществляются через JWT-токены на основе ролей (Chief, Manager, Worker, StoreDirector).
- Все ошибки API возвращаются в структурированном формате **Problem Details** (RFC 7807) с единообразным набором полей: `type`, `title`, `status`, `instance`, `traceId`, `code`. Для ошибок валидации дополнительно возвращается объект `errors` с деталями по каждому полю. Поле `code` — это `ErrorCodes` enum (`NOT_FOUND`, `CELL_OCCUPIED` и т.д.), единый источник правды для бэкенда и фронтенда.
- Бизнес-правила покрыты модульными тестами для ключевых сценариев (приёмка, резервирование, перемещение).
---

## 2. Складская иерархия

- **Warehouse** – склад.
- **Zone** – зона склада: `Normal`, `Fridge`, `Freezer`.
- **Rack** – стеллаж с буквенным обозначением, уникальным в пределах зоны.
- **Shelf** – полка с номером, уникальным в пределах стеллажа.
- **Cell** – ячейка с кодом, уникальным в пределах полки.

Правила:
- Удаление стеллажа, полки или ячейки разрешено **только если они не содержат партий** (проверка `Cell.IsOccupied` или наличие связанных `Batch`).
- При создании ячейки флаг `IsOccupied` устанавливается в `false`.

> **Ошибка при нарушении.** При попытке удаления объекта, на который
> ссылаются связанные записи (партии, строки документов), API возвращает
> `400 Bad Request` с кодом `CANNOT_DELETE_REFERENCED` и русским
> сообщением. Это универсальный код для всех случаев FK-violation,
> вне зависимости от уровня иерархии.

---

## 3. Товары (Product)

- **Товар** – справочная сущность, не содержит информации о текущих остатках.
- Поля: `Name`, `Manufacturer`, `Supplier`, `Category`, `Unit`, `MinStockThreshold`.
- `MinStockThreshold` – минимальный допустимый суммарный остаток товара по всем партиям (доступное количество, т.е. `Quantity - ReservedQuantity`). При достижении или превышении этого порога генерируется уведомление менеджерам.

---

## 4. Партии (Batch)

- Партия всегда привязана к конкретному товару (`ProductId`) и конкретной ячейке (`CellId`).
- Партия имеет:
    - `Quantity` – фактическое количество на складе.
    - `ReservedQuantity` – суммарное количество, зарезервированное под активные отгрузки (всегда ≤ `Quantity`).
    - `PurchasePrice` – закупочная цена за единицу.
    - `ProductionDate`, `ExpiryDate`, `ReceivedDate`.

### Правила работы с партиями:

- **При создании партии** (приёмка):
    - Ячейка должна быть свободна (`IsOccupied == false`).
    - Устанавливается `IsOccupied = true`.
    - `Quantity` устанавливается равным фактическому количеству.
    - `ReservedQuantity = 0`.
    - Создаётся `InventoryTransaction` типа `In`.

- **Правила валидации при создании партии:**
  - `ProductionDate` не может быть в будущем (`<= today`) — FluentValidation.
  - `ExpiryDate` должен быть в будущем (`> today`) — FluentValidation.
  - `ExpiryDate` должен быть строго позже `ProductionDate` — FluentValidation **и** CHECK constraint `CK_Batches_ExpiryAfterProduction` на уровне БД.

> **Следствие.** Через API нельзя создать партию, срок годности которой
> уже истёк. Просроченные партии появляются естественным образом со временем.
> Для наполнения БД тестовыми просроченными партиями используйте SQL-скрипты —
> API такие данные не пропустит.

- **При перемещении партии** в другую ячейку:
    - Новая ячейка должна быть свободна (`IsOccupied == false`).
    - Старая ячейка освобождается (`IsOccupied = false`).
    - Новая ячейка занимается (`IsOccupied = true`).
    - Создаётся `InventoryTransaction` типа `Move` с указанием `OldCellId` и `NewCellId`.
    - Другие поля партии не меняются.

- **При списании просрочки или брака**:
    - Списывается только доступное количество (`Quantity - ReservedQuantity`).
    - `Quantity` уменьшается на списываемую величину.
    - Если после списания `Quantity` становится 0, ячейка освобождается (`IsOccupied = false`).
    - Создаётся `InventoryTransaction` типа `WriteOff` (отрицательное изменение).

- **При отгрузке (расходе)**:
    - Сначала снимаются резервы (см. раздел резервирования).
    - Затем уменьшается `Quantity` на отгружаемое количество.
    - Если `Quantity` становится 0, ячейка освобождается.
    - Создаётся `InventoryTransaction` типа `Out`.

- **При резервировании** (см. раздел 6) – `ReservedQuantity` увеличивается, но `Quantity` не меняется.

### Формат дат

`ProductionDate`, `ExpiryDate` и `ReceivedDate` хранятся в БД как `date`
(без времени) — это семантические **даты**, а не моменты времени.
В API передаются строками в формате `yyyy-MM-dd` (`2026-09-01`).

Системные поля-моменты (`InventoryTransaction.Timestamp`, `CreatedAt`,
`ConfirmedAt`, `ShippedAt`, `ReceivedAt`, `RejectedAt` и т.п.) остаются
`timestamptz` — это точки во времени, а не даты.

## 5. Приёмка товаров (Receipt)

- **Receipt** – документ, создаваемый менеджером со статусом `Pending`.
- Содержит ожидаемые позиции (`ExpectedLines`): `ProductId`, `ExpectedQuantity`.
- Подтверждение приёмки выполняет **менеджер или работник** через эндпоинт `PUT /api/receipts/{id}/receive`.
- В запросе на подтверждение передаются фактические позиции:
    - `ProductId`
    - `ActualQuantity` – фактически поступившее количество
    - `CellId` – ячейка для размещения
    - `ExpiryDate` (тип `date`, формат `yyyy-MM-dd`)
    - `PurchasePrice`
- Правила:
    - Для каждой позиции создаётся отдельная партия (`Batch`), если `ActualQuantity > 0`.
    - Если `ActualQuantity` отличается от `ExpectedQuantity`, разница (в абсолютном значении) записывается в поле `Comment` документа `Receipt`.
    - Ячейка должна быть свободна перед созданием партии.
    - Статус документа становится `Received`.
    - При создании партии генерируется транзакция прихода (`In`).
- **Отклонение приёмки** (Manager/Chief):
  - Доступно только для документа в статусе `Pending`.
  - Статус документа становится `Rejected`, фиксируется `RejectedAt`.
  - Отклонение не создаёт партий и не меняет остатки.
---

## 6. Резервирование

- Резервирование выполняется при подтверждении (`Confirm`) заказа на отгрузку (`SupplyOrder`).
- Для каждой позиции заказа система ищет доступные партии одного товара.
- Доступное количество партии = `Batch.Quantity - Batch.ReservedQuantity`.
- Резервирование происходит **последовательно** по партиям (порядок не важен, но можно сортировать по `ExpiryDate` для FIFO).
- Если суммарного доступного количества по всем партиям товара достаточно для выполнения позиции, то:
    - Для каждой партии создаётся запись `Reservation` с указанием `BatchId`, `SupplyOrderId`, `Quantity` (часть от общего заказа).
    - `Batch.ReservedQuantity` увеличивается на зарезервированное количество.
- Если доступного количества не хватает хотя бы для одной позиции, заказ **не подтверждается** и возвращается ошибка.
- При отгрузке (`Ship`) резервы для данного `SupplyOrder` удаляются, а `Batch.ReservedQuantity` уменьшается на соответствующие величины.

---

## 7. Отгрузки (SupplyOrder)

- **SupplyOrder** – документ, создаваемый менеджером со статусом `Draft`.
- Может быть создан на основе заявки магазина (`SupplyRequest`) или без неё.
- Содержит позиции: `ProductId`, `Quantity`.

### Статусы и переходы:
- `Draft` → `Confirmed` – через эндпоинт `/confirm`. Выполняется резервирование.
- `Confirmed` → `Shipped` – через эндпоинт `/ship`. Выполняется списание остатков, удаление резервов.
- Если резервирование не удалось, статус остаётся `Draft`, заказ не подтверждается.

### Правила при подтверждении (`Confirm`):
- Проверяется достаточность доступных остатков по всем позициям.
- Если достаточно – создаются `Reservation`, обновляется `ReservedQuantity`, статус → `Confirmed`.
- Если нет – возвращается ошибка.

### Правила при отгрузке (`Ship`):
- Доступно для работника (Worker) или менеджера.
- Проверяется, что заказ в статусе `Confirmed`.
- Для каждой позиции:
    - Находятся все резервы, относящиеся к этому `SupplyOrder`.
    - Для каждого резерва:
        - Уменьшается `Batch.Quantity` на зарезервированное количество.
        - Уменьшается `Batch.ReservedQuantity` на это же значение.
        - Резерв удаляется.
        - Создаётся транзакция `Out`.
    - Если после уменьшения `Quantity` становится 0, ячейка освобождается (`IsOccupied = false`).
- Статус заказа → `Shipped`.

---

## 8. Заявки магазина (SupplyRequest)

- **SupplyRequest** – создаётся директором магазина (`StoreDirector`) со статусом `Draft`.
- Может быть отправлена на рассмотрение (`Submit`) – статус → `Submitted`.
- Менеджер может одобрить (`Approve`) – статус → `Approved`, или отклонить (`Reject`) – статус → `Rejected`.
- На основе одобренной заявки менеджер создаёт `SupplyOrder` (с указанием `SupplyRequestId`).
- После создания заказа заявка может быть переведена в `Completed` (опционально, но в упрощённой модели мы не делаем автоматического перехода).

---

## 9. Перемещение партий

- Перемещение инициируется менеджером через эндпоинт `PUT /api/batches/{id}/move`.
- Тело запроса содержит `cellId` – целевую ячейку.
- Правила:
    - Целевая ячейка должна существовать и быть свободной (`IsOccupied == false`).
    - Текущая ячейка освобождается.
    - Целевая ячейка занимается.
    - Обновляется `Batch.CellId`.
    - Создаётся транзакция `Move` с `OldCellId` и `NewCellId`.
- Перемещение разрешено для партий с любым `Quantity` (в том числе нулевым, но это бессмысленно, обычно проверяют `Quantity > 0`).

---

## 10. Списание просрочки

- Инициируется менеджером (через отдельный эндпоинт или вручную).
- Для списания просроченных партий проверяется `ExpiryDate < Today`.
- Списание выполняется на всё просроченное количество (`Quantity - ReservedQuantity`).
- Если `ReservedQuantity` > 0, то списать можно только доступный остаток; резервы не затрагиваются (предполагается, что просроченный товар не должен резервироваться, но в упрощённой модели это допустимо).
- Создаётся транзакция `WriteOff`.
- Если после списания `Quantity == 0`, ячейка освобождается.

---

## 11. Уведомления

- Генерируются фоновым сервисом, запускаемым периодически (например, каждый час).
- Два типа уведомлений:
    1. **О приближающемся сроке годности**: если `ExpiryDate - Today <= 3` дня, создаётся уведомление для всех менеджеров.
    2. **О низком остатке**: если сумма доступных остатков по всем партиям товара (`Quantity - ReservedQuantity`) < `Product.MinStockThreshold`, создаётся уведомление для менеджеров.
- Уведомления хранятся в таблице `Notification` и доступны для просмотра и отметки о прочтении через API.
- Уведомления генерируются фоновым сервисом с использованием фильтрующих запросов к БД:
  - `GetBatchesByExpiryDateRangeAsync` для партий с истекающим сроком.
  - `GetLowStockProductsAsync` для товаров с суммарным остатком ниже порога.
- Фоновый сервис использует репозитории напрямую, а не сервисы. Он не зависит от бизнес-сервисов, а только от репозиториев для чтения данных, что повышает производительность и уменьшает количество запросов.
---

## 12. Аудит (InventoryTransaction)

- Каждая операция, изменяющая физическое количество товара (`Quantity`) или перемещающая партию между ячейками, создаёт запись `InventoryTransaction`.
- **Изменения `ReservedQuantity` (резервирование) не фиксируются в аудите**, поскольку это не физическое движение, а лишь блокировка товара под будущую отгрузку. Резервирование отслеживается отдельно через таблицу `Reservation`.
- Поля:
    - `BatchId` – ссылка на партию.
    - `QuantityChange` – изменение (положительное для прихода, отрицательное для расхода/списания, для перемещения 0).
    - `TransactionType` – `In`, `Out`, `Move`, `WriteOff`.
    - `DocumentId` – ссылка на `ReceiptId` (для прихода) или `SupplyOrderId` (для расхода).
    - `UserId` – идентификатор пользователя, выполнившего операцию.
    - `Timestamp` – дата/время (UTC).
    - `OldCellId`, `NewCellId` – для перемещений.
- Транзакции **никогда не обновляются** – только вставка (журнал).
- При ручном создании партии (через отдельный эндпоинт) `DocumentId` остаётся `null`.

## 14. Дополнительные ограничения

- **Частичное резервирование** разрешено: одна партия может резервироваться частями для разных заказов.
- **Расхождения при приёмке** не блокируют операцию, а фиксируются в комментарии.
- **Удаление документов** не предусмотрено (можно только менять статусы).
- **Автоматическое обновление статусов** не выполняется (все переходы инициируются вручную через API).

---

## 15. Жизненный цикл документов (упрощённо)

- **Receipt**: `Pending` → `Received` (при подтверждении) или `Pending` → `Rejected` (при отклонении).
- **SupplyRequest**: `Draft` → `Submitted` → `Approved` / `Rejected`.
- **SupplyOrder**: `Draft` → `Confirmed` (после резервирования) → `Shipped` (после отгрузки).

Все переходы проверяются простыми условиями в сервисах.

## 16. Коды бизнес-ошибок

Каждая бизнес-ситуация, приводящая к ошибке, имеет **уникальный машиночитаемый код**, возвращаемый в поле `code` ответа. Коды определены в `Wms.Core.Constants.ErrorCodes` как **C#-enum** со строковыми значениями `SNAKE_CASE`. Enum генерируется в TypeScript-клиент через NSwag, что гарантирует совпадение кодов на бэке и фронте. Использование строковых литералов вместо enum в коде не допускается — компилятор ловит опечатки.

Фронтенд определяет сценарий обработки по коду, а не по тексту.

> **Важно не путать с доменными статусами.** `ErrorCodes` описывает **ошибки** и сериализуется в `SNAKE_CASE` через `[EnumMember]`. Доменные статусы документов (`ReceiptStatus`, `SupplyOrderStatus`, `SupplyRequestStatus`) и типы операций (`TransactionType`) — это **состояние документа**, а не ошибка. Они сериализуются как `PascalCase`-строки (`"Pending"`, `"Draft"`, `"In"`) через `JsonStringEnumConverter`.

### Список кодов

|-----|:----:|----------|

### Использование на фронтенде

Благодаря автогенерации TS-enum через NSwag, фронтенд работает с кодами типобезопасно. Значения enum совпадают с реальным JSON (`SNAKE_CASE`), что делает код самодокументируемым:

```typescript
import { ErrorCodes, WmsProblemDetails } from './wms-api';

function handleApiError(error: WmsProblemDetails) {
  switch (error.code) {
    case ErrorCodes.NOT_FOUND:
      showToast('Ресурс не найден');
      break;
    case ErrorCodes.VALIDATION_FAILED:
      highlightFields(error.errors);
      break;
    case ErrorCodes.CELL_OCCUPIED:
    case ErrorCodes.TARGET_CELL_OCCUPIED:
      highlightCell();
      break;
    case ErrorCodes.UNAUTHORIZED:
      redirectToLogin();
      break;
    case ErrorCodes.FORBIDDEN:
      showToast('Недостаточно прав');
      break;
    default:
      showToast(error.title ?? 'Неизвестная ошибка');
  }
}
```

Компилятор TypeScript ловит опечатки в кодах. При добавлении нового кода на бэке достаточно перегенерировать TS-клиент — компилятор подскажет все места, где нужен новый `case`.
